# Form workflow rules

One tool-level rule decides which form workflows work in iMIS, which iMIS cannot do, which are unsafe, and which carry a caveat. Every forms tool reads the same table (`src/services/forms/shared/form-workflow-rules.ts`): the form writer's approval check, the Forms display contract and every Forms placement, the form writer's post-processing check, `imis_form_post_processing`, the form-group lifecycle, and `imis_form_plan`. Results name the rule (`ruleId`), its class, iMIS's own reason with the help page, and the routes that work.

Classes:
- **Works**: build it.
- **Allowed with caveats**: build it; the caveat is in the plan the person approves.
- **Not yet proven**: build it only as an unproven route and never call it working; it takes its real class once its live proof on AZFX records is recorded.
- **Impossible in iMIS**: refused, with iMIS's reason and the routes that work.
- **Unsafe**: refused, with the reason.

How to use it:
- For a membership application, call `imis_form_plan`: `workflowRules.membershipApplicationRoutes` gives routes A, B and C with their classes. Offer the person every route; do not pick one for them.
- Sign-up fields never go on an approval form (W1), and a page never creates the contact for one (W5): create the account with a separate form without approval (W2), then use the approval form for the signed-in applicant (W4).
- The applicant's requested member type goes in a custom field (W8): iMIS keeps Member Type read-only on every form.
- A post-processing script that changes membership is W10 on an approval form and W12 without one, and W12 has no exception: such a script always needs form approval. `imis_form_builder_write` and `imis_form_post_processing` refuse to bind it to a form without approval; `imis_form_builder_write` (form update) and the form-group lifecycle in `imis_form_administration` (group update or delete) refuse to switch approval off where a bound script changes membership or cannot be verified; and no page places such a form. A script page replaced in place (`imis_page_iparts`, or `imis_document` update, snapshot restore or publish) is judged against every form that runs it, and `imis_form_runtime_submit` never submits a form without approval whose script changes membership. Put the form, or its form group, behind approval first. Not yet enforced: `imis_configuration_import`, `imis_website_migration`, and form history restore in `imis_form_administration`.

| Rule | Combination | Class | Reason or caveat | Routes that work |
|---|---|---|---|---|
| W1 | Sign-up fields (Username, Password) on a form that requires approval, directly or through its form group | Impossible in iMIS | iMIS: for approval processes that involve creating an account, the Create Account step must be separate and not require approval, because the iMIS ID must be known before an approval can be processed. | W2, W4 |
| W2 | Account-creation form: sign-up fields with Contact First name, Last name and Email, on a page set to create the contact, without approval | Works | The native Create Account form. |  |
| W3 | The page creates the contact with a fixed member type and billing category | Works | The Forms content item sets one member type for everyone who uses that page; applicants can choose a type by choosing among pages. |  |
| W4 | Approval form for a signed-in applicant whose record already exists, with contact, address and panel fields, including a custom field holding the requested membership type | Works | Changes wait in the approval queue; approving applies them, and staff may untick single changes. |  |
| W5 | The page creates the contact for a form that requires approval | Impossible in iMIS | iMIS: the iMIS ID must be known before an approval can be processed, so the contact must be created by a separate form that does not require approval. | W2, W4 |
| W6 | Anonymous approval form locked to one named contact, writing a multi-instance source | Works | The documented anonymous-approval pattern. |  |
| W7 | A form that requires approval with a file upload, a Multi Layout, or Where/Where multi-instance load and save | Impossible in iMIS | iMIS: file uploads and multi-instance layouts update iMIS directly and cannot be intercepted before they are saved, and the Where clause is not supported with Approvals. | W4 |
| W8 | The Member Type or Company Member Type contact field as an editable answer, on any form | Impossible in iMIS | iMIS: the Member Type and Company Member Type properties in iMIS Forms are read-only and cannot be changed. | W3, W4, W9, W10, W11 |
| W9 | Staff set the member type themselves after approving the application | Works | A staff change on the contact's record. Caveat: Changing a member type does not create dues or an invoice; billing uses the new type from the next cycle. |  |
| W10 | A post-processing script on a form that requires approval, which sets the contact's member type (or another membership field) from the application when staff approve it | Not yet proven (then Allowed with caveats) | iMIS runs the form's post-processing step when a submission is approved, in the approving staff member's session. No REST route that sets a contact's member type is proven yet. Caveat: It changes the membership field only: no dues and no invoice, and billing uses the new type from the next cycle. If staff untick the requested answer, the script finds no value and changes nothing. A post error stops post-processing until staff fix it in iMIS. | W9, W11 |
| W11 | The standard Join Now page for the membership, with a separate approval form for supporting answers | Works | Join Now owns the member type choice, dues and checkout; it has no staff approval step of its own. |  |
| W12 | A post-processing script that changes member type, member status, paid-through date, billing category or company administrator role, on a form that does not require approval | Unsafe | Without approval the script runs in the submitter's own session, so an applicant would be setting their own membership with no staff decision. A script that changes membership always needs form approval: AgentZ will not bind one to a form without approval, will not switch approval off on a form or form group whose bound script changes membership, and will not place such a form on any page. | W10, W9 |
| W13 | A post-processing script that writes to a contact other than the submitter or the on-behalf-of contact | Unsafe | A form is bound to one ID; writing to another contact acts outside the submission. The post-processing owner binds every write to {{ID}}. |  |
| W14 | Card or bank details in a form field, or a payment taken in post-processing | Unsafe | Payment belongs to Join Now, Cart, Payment Creator or Pay Central, never to a form response. | W11 |
| W15 | A post-processing script that reads Multi Layout row values as main-form answers | Impossible in iMIS | iMIS: values in multi-instance layouts are saved at once, so they are not available to post-processing. |  |
| W16 | A form whose page creates the contact without sign-up fields, with fields beyond first name, last name and email | Impossible in iMIS | iMIS: if the account sign-up fields are absent, any additional information entered is not saved. | W2 |
| W17 | A form that requires approval, with post-processing | Allowed with caveats | Post-processing runs after the submission is approved. Caveat: A post error stops post-processing; staff must fix the cause in iMIS, because a submission with a post error cannot be resubmitted. |  |
