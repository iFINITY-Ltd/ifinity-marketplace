# BuildHub preview renderer

The shared, self-contained renderer that draws an `ifinity.buildhub.preview.v2` model (v1 tolerated) the way iMIS itself renders a page. The AgentZ companion and the BuildHub site vendor this folder as-is; the MCP builds it and never executes it.

| File | What it is |
| --- | --- |
| `buildhub-preview.js` | One pure ES module built from `src/buildhub-preview/` by `scripts/build-buildhub-preview.mjs` (`npm run build:buildhub-preview`; `npm run verify:buildhub-preview` fails when it is stale). Exports `renderPage`, `renderArtifact`, `packageCoverage`, `presentationManifestFor`, `rendererStylesheet`, `inlineFonts`, `sanitiseFragment` and `BUNDLED_FONTS`. No network, no DOM access, no timers, no dynamic imports — the build refuses a bundle that references any of them, so a host can seal the output in a frame with `default-src 'none'` (fonts are `data:` URIs). |
| `manifest.json` | Renderer, stylesheet and plugin versions, the bundle's sha256, the catalogue's version and sha256, and the font families with their licence — the host records these beside what it rendered. |
| `stock-layouts.json` | The 48 DefaultSystem content layouts (`ifinity.buildhub.stock-layout-catalogue.v1`, captured read-only from ukdemoaisp9 on 2026-09-12) keyed by DocumentVersionId and path, each with its zone map and a sha256 of its markup. The assembler resolves a page's layout key against it; the renderer draws from it. A layout the catalogue lacks is drawn in a single column under a visible label. |
| `stock-shells.json` | The stock site shells (`ifinity.buildhub.stock-shell-catalogue.v1`, generated by the build from the tracked ukdemoaisp9 capture of 2026-09-22 and checked by `verify:buildhub-preview`): the 5 stock website layouts (WSL) with their zone slots, the 4 stock website templates (WST) with their placements (ContentHtml bodies recorded as byte count and sha256 only) and a content fingerprint the exporter compares a tenant's copy against (a stock shell edited in place is packaged, not declared standard), and the 10 platform themes that have no theme package, each saying whether this renderer reproduces it (Orion, Flat_White) or not. A page whose declared site binding names a stock template or layout is drawn from here. |
| `fonts/` | The faces the two stock shells measure, as woff2 (latin subset) with each family's SIL Open Font License text beside it: Red Hat Display, Open Sans, Inter (Orion, staff), Poppins (Flat_White, member) and Montserrat (declared by the Orion theme's `@import`, unused by its measured rules, kept for the specimen). `fonts-manifest.json` lists every face with weights, bytes and sha256. Refetch with `node --dns-result-order=ipv4first scripts/fetch-buildhub-preview-fonts.mjs`. |

## Calling it

```js
import { renderPage, renderArtifact, packageCoverage, BUNDLED_FONTS } from "./buildhub-preview.js";
import catalogue from "./stock-layouts.json" with { type: "json" };
import shellCatalogue from "./stock-shells.json" with { type: "json" };

const material = { file: (path) => bundleFiles.get(path) }; // preview-relative files of the bundle
const page = renderPage(model, "@/Site/Page", { material, catalogue, shellCatalogue, fonts: BUNDLED_FONTS, viewport: "desktop" });
frame.srcdoc = page.html;          // sealed frame: sandbox="" + CSP default-src 'none'; font-src data:
page.coverage;                     // per placement: material / drawn / runtime / appRuntime / note, fonts inlined and missing
const view = renderArtifact(model, "$/Common/Queries/…", { material, fonts: BUNDLED_FONTS }); // host-side definition view
const themeSpecimen = renderArtifact(model, "theme:Orion", { material, fonts: BUNDLED_FONTS });
const report = packageCoverage(model, { material, catalogue, fonts: BUNDLED_FONTS });
```

`renderPage` draws only from the model's own material: the audience shell (staff Orion header, sidebar with iMIS's standard navigation and the model's own tree, mobile navigation bar; member Coffee/Flat_White utility bar, logo, standard and model primary navigation, footer — see "Renderer 1.4.0"), the stock or packaged layout in iMIS's exact wrapper chain (`WTZone > ContentPanel > layout rows/cols > ContentItemContainer > WebPartZone<N>_Page1 > iMIS-WebPart > ste_container_ci<Name> > panel`), the placement's panel chrome (heading only with ShowTitleFlag, border only with ShowBorder; ContentHtml bare, as iMIS draws it), and a per-type inner rendering (query grids, SVG charts, progress trackers, query templates, panel definitions, inert Form Builder markup, client application containers, tab strips, big-button panels, and labelled facsimiles or placeholders for everything the package cannot reproduce). Fonts come from the model's `theme.stockShells` manifest; a family the bundle lacks is reported in the coverage with its declared fallback, never swapped silently.

## Notes inside the frame (renderer 1.2.0)

Everything the renderer writes inside the frame for the people browsing a listing — the labels on placements drawn from settings or sample data, the client-app banner, layout and website-design fallbacks, font substitutions — is plain words for association staff: what they are looking at (a close likeness, sample data, an app's outer frame) and what is left out and why (records a signed-out visitor may not see, content other websites fill in, password and key fields). It never mentions how the preview works. The technical reasons — why an app can or cannot run, what the package carries, what the host passed — are in the page's `coverage` (placement `note`, `siteShell.notes`, `fonts.missing` / `fonts.synthesised`), for the host's own diagnostics. **Hosts must not restate the in-frame notes** (no second banner, no paraphrase beside the frame); a host that shows diagnostics draws them from the coverage, outside the frame, for its own operators. `tests/unit/buildhub-preview/frame-notes.test.ts` renders every corpus page and every captured website and fails if an in-frame note mentions readiness, verification, packs, protocol, fingerprints or leases.

## Site shells (renderer 1.2.0)

When the package declares which website a page belongs to and that website's template (`model.shells`, material under `preview/shells/`), `renderPage` draws the page inside that template instead of the audience shell: the website layout's markup with each slot as iMIS draws it (`div#WTZone<N>_Page1.WTZone`, root `ctl01_masterWrapper`), the template's placements by role (navigation from the model's tree, ContentHtml as sanitised markup, per-site content areas as labelled placeholders because iMIS resolves them per website at run time), and the page itself in the main-content zone (`div#mainContentWrapper.ContentPanel`). A packaged theme's stylesheets are written into the frame after `sanitiseCss`; its external `url()` addresses were already declared as omissions by the assembler and are never fetched. What may be drawn for each shell is decided once, when the model is assembled, and carried as `shell.material`: `packaged` (the package's material), `declared-stock` (a platform shell the package declared standard — a layout or template drawn from `shellCatalogue` only when the catalogue entry's `payloadSha256` equals the one the model carries, a theme by name) or `unavailable` (nothing, with the reason). The renderer never falls back from one to another: a layout the package does not declare, a stock shell whose catalogue fingerprint differs, or a theme not declared is drawn as unavailable. The stock Orion and Flat_White themes use this renderer's own rules; any other declared platform theme is drawn with base rules and reported as not reproduced. Pass `siteShell: false` to force the audience shells. The coverage gains `coverage.siteShell` (`packaged-template` / `stock-template` / `audience-fallback`, the layout and theme sources, one row per template placement, notes) and `fonts.shellTheme` / `fonts.shellFaces`, where each theme face is `material` (packaged and licensed, inlined), `drawn` (supplied by the renderer's bundled faces) or `runtime` (only the live site can draw it; the named fallback is used). `resolveSiteShell`, `renderSiteShell` and `readShellFile` are exported for hosts that inspect the shell without drawing a page.

## Client application runtime

`resolveRuntimeRequest(pack, material, { method, url, headers, body })` answers one intercepted `/api` request from a package's runtime data pack (`preview/runtime/<package>.shim.json`, read with `readRuntimePack`); `runtimeStubsHtml(pack)` gives the `__ClientContext` and `RequestVerificationToken` fields the frame mounts first; `appRuntimeReadiness(entry, material, pack, entryFile)` says whether to run the app at all (the pack must be that package's own and name that entry set; every promise it makes is re-checked with the resolver's own checks — `queryRows`, `contentItemSettings`, `unanswerablePromises`). Since `1.2.0` the resolver also answers the `business-object` family — `GET api/<BO>` (paging, equality filters on declared properties) and `GET api/<BO>/<id>` from a package's consented panel-source rows (`findRuntimeBusinessObject`, `businessObjectRows`, `readBusinessObjectRows`, `businessObjectEndpointProblem`) — and `resolvePackageMember` resolves a member reference, with its bytes, the way readiness and the resolver do (iMIS's `/iPartSource/<zip>/` prefix is the package root; `resolvePackageReference` gives the bare path). The resolver answers the frame's own `GET /iPartSource/<this zip>/<member>` with the member (answered `member`; binaries as base64 with `bodyEncoding`). Tenant-identity routes, `/_self` routes and Business Objects whose own definition refuses a signed-out visitor answer exactly what iMIS returned to a signed-out visitor on a real page (`signed-out-visitor.ts`, whose single source `signed-out-visitor-probe.json` is recorded from `/iFINITY/Video_Library.aspx` on ukdemoaisp9: `signedOutVisitorAnswer`, `SIGNED_OUT_VISITOR_RESPONSES`, `isAnonymousVisitorRoute`, `signedOutRefusal`, `SIGNED_OUT_REFUSAL_STATUS`/`BODY`); `api/User` and `api/CsContact` lists answer an empty PagedResult because iMIS gives a signed-out visitor a real record there, which the preview never carries (1.5.0); the endpoint is judged before the token; secret fields are never served (`secrets.ts`); readiness returns `{ blockers, notLoaded, signedOut }` — outside origins are listed as not loaded and Business Objects closed to the signed-out visitor as `signedOut`, not blockers. The contract — envelopes, paging, not-available and rejected-write bodies, the frame's sandbox and CSP — is `docs/BUILDHUB_PREVIEW_RUNTIME.md`.

## Renderer 1.3.1

`body#MainBody` carries iMIS's own classes in iMIS's order — the website template's wrapper class, the page's, and `body-main sidebar-fixed` on the staff master only — before the renderer's `bhp-*` classes. `appRuntimeReadiness` resolves import-map addresses from the entry document (with `scopes` and prefix keys), scans `url()` as CSS with comments and strings skipped, and returns `siteImages`: pictures the app's sample records name at the website's own paths, which the package does not carry (the resolver answers a GET for one in plain words). Details: `docs/BUILDHUB_PREVIEW_RUNTIME.md` §10.

## Renderer 1.4.0 — stock shell fidelity

The two stock shells were measured on ukdemoaisp9 at 375, 768 and 1280 px (2026-09-23; the staff site live and signed in, the member site live and signed out) and the readings are recorded in `tests/fixtures/buildhub-preview-corpus/shell-fidelity/native-geometry.json`; `src/buildhub-preview/shell-geometry.ts` holds the same numbers, the stylesheet writes its shell rules from them, and `tests/unit/buildhub-preview/shell-fidelity.test.ts` asserts both against the record.

- **Staff (Orion, Constellations.master).** Breakpoints 767 / 768–991 / 992. Above 767 px the master's start-up script leaves `nav-expanded js-nav-sticky` on the wrapper, so the renderer bakes those classes for the tablet and desktop viewports and omits them for phone. The 250 px sidebar stands beside the content from 768 px; iMIS keeps it `position: fixed` and moves its top with the header as the page scrolls (`setNavTop`), and the frame draws the same behaviour without a script as a sticky sidebar spanning the content rows, clipped by the wrapper as the master's `overflow-x: clip` does. The tree scrolls on its own in `.sub-nav-body` (`max-height: 100vh`, 200 px bottom padding, 10 px scrollbar); the page scrolls in the document. Header 73 / 58 / 92 px (search field from 992 px only; the header's icons wrap to a second row on a phone), sidebar toggle row 62 / 48 px, tree rows 56 px, content `#eeeeef` with `.main` padding `40px 20px 0`, footer 50 px (115 px on a phone), and at 767 px and below the sidebar is hidden and the fixed 64 px mobile navigation bar takes its place. `body` keeps iMIS's served classes: the script's `fade`, `loaded` and `in` only gate transitions, so a static frame has nothing to reproduce for them.
- **Member (Coffee template, Flat_White theme), as a signed-out visitor sees it.** Breakpoint 991 / 992. The header is a grid — logo, utility, primary navigation stacked to 991 px (utility row white and centred, the primary navigation collapsed behind the menu toggle, which is its resting state), and a 50 px `#252E38` utility bar over logo and navigation from 992 px — content padding 15 / 30 px on a `#fcfcff` page, the back-to-top button fixed at the bottom right, and a navigation / contact / copyright footer (`2fr 1fr` from 992 px).
- **Standard navigation.** The stock shells draw iMIS's standard navigation for context, marked "Standard iMIS navigation shown for context; this configuration does not change it.", with the package's own navigation placed where its paths put it (a node whose parent path is a standard node goes under it; any other is placed after the standard roots; a node naming a standard path joins it) and marked with an accent. The staff tree is the Staff site sub-navigation iMIS rendered for a staff user (13 groups, 293 items, in rendered order, top-level icon classes kept); the member menu is the stock Coffee site's root menu a signed-out visitor sees (About, Membership, Events, Shop, Give Now, Communities, Certification; Manage appears only when signed in). `src/buildhub-preview/stock-navigation.json` holds both, extracted by `tests/fixtures/buildhub-preview-corpus/EXTRACT_NAVIGATION.py`.
- **How stock was separated from the tenant's own.** Each rendered item was matched to its NAV document by parent path and label. It is standard when that document is `IsSystem=true`, or was created by an account that created `IsSystem=true` navigation and never created the tenant's own navigation (the tenant's accounts are the creators of non-system navigation created in 2025 or later). An item whose parent is not standard is dropped with its children. The tenant's items are counted (62 staff, 4 member) and never recorded, so no tenant label, path or target is in the file.
- **Icons and logo (`shell-assets/`).** The shells draw the themes' own icons as the themes do — CSS masks coloured by the rule — from bundled copies: Orion's `NavbarSprite.svg` (group icons, sidebar toggle, tree carets), `IconSprite.svg` (header search, cart, easy edit, batch, on-behalf-of, account caret) and `bento-menu.svg` (app menu), Flat_White's `auxIcons.svg` (cart, account, search, menu, carets, back-to-top), and the iMIS logo from the iFINITY brand folder scaled into the header's 119 × 35.2 px box. `shell-assets/shell-assets-manifest.json` records each source's URL, bytes, sha256 and owner; `tests/fixtures/buildhub-preview-corpus/EXTRACT_SHELL_ASSETS.py` derives `src/buildhub-preview/shell-assets.json` (one standalone SVG per symbol, the scaled logo) and the build refuses a source whose hash has changed. They are data: URIs in the frame; a staff page carries only the group icons its own tree uses. These files are Advanced Solutions International's iMIS theme artwork, reproduced for preview fidelity; none declares a licence.
- **What the shells still do not draw.** The website's own logo, header background and footer content are per-website content the renderer labels rather than invents; the sidebar's collapsed 62.5 px rail and flyouts, the expanded menus and every other state a click produces are not drawn, because the frame shows the resting state only.

## Renderer 1.5.0 — always previewable

Every packaged client app runs in the sealed frame with or without sample data. `resolveRuntimeRequest` answers a data call the package carries no records for with a valid empty answer of iMIS's shape (answered `empty`: `emptyEnvelope` — an empty `PagedResult` — for `api/Query` and Business Object lists, the placement record with `Settings: ""` for `api/ContentItem`, a plain-words 404 for one Business Object row), with `$preview` (`EMPTY_PREVIEW_MARKER`) and `$previewNote` saying why. `appRuntimeReadiness` never blocks for missing data: it returns `empty` (calls shown with no records) and `unanswered` (routes answered with a plain-words 404) as declared states, and blocks only when the app's code cannot be served or the pack contradicts its material, naming the files in `missingFiles` — the frame names them in plain words. Packs written before 1.5.0 are read as they are: their data rows marked `unavailable` are answered empty. The model's `clientPackages[].sampleRecords` lists what is packaged and what is empty. Contract: `docs/BUILDHUB_PREVIEW_RUNTIME.md` §11.

## Renderer 1.5.1 — readiness is the single source

Hosts decide nothing about whether an app runs: `clientAppReadiness(model, material, sourcePath)` returns `ready`, the verdict (`blockers`, `notes`, `missingFiles` and the declared states) and the pack the frame answers from, and hosts show it as it is — never filtering, rewriting or supplementing `blockers`, `notes` or `missingFiles`, never scanning an app's code, never recovering a pack. Readiness parses the entry document with parse5 (the WHATWG HTML parsing algorithm, MIT, with its entities tables, BSD-2-Clause; bundled, pure), walks stylesheets rule by rule as CSS Syntax does to honour only the `@import`s browsers honour, parses the app's scripts with acorn (bundled; the bundle stays pure), follows only what the entry document actually loads (static and literal dynamic imports, workers, `importScripts`), resolves every module name through the document's import map as the HTML specification does, and blocks only on certainty: for missing code the app certainly loads (following the ES module lifecycle — a graph's loading stops at its first failure — and ending a run at any expression not on the completion whitelist, each of whose forms is justified from the specification's evaluation steps as calling nothing the page can replace) or for the app's identity. The rules are checked against V8's own module loader over generated programs (`tests/fuzz/`; 5,000 apps in the unit suite). A load that may not happen is a note naming the file; the app runs, and if that load fails the frame's request log shows it. Scope resolution is eslint-scope 8 (with esrecurse 4 and estraverse 5, all BSD-2-Clause), bundled here: one scope model per script, read by every rule that needs to know what a name refers to. `loadRuntimePack` carries the compatibility path for packs written before §11 (broken promises withdrawn, a pack refused for its data read with no data), and `modelReadiness(model).legacyModel` is the verdict for a v1 model. Contract: `docs/BUILDHUB_PREVIEW_RUNTIME.md` §11 items 7–12.

## Provenance

Stylesheet rules are re-expressed from the captured `10-UltraWaveResponsive.css`, `99-Orion.css`, `99-Flat_White.css` and `50-FormBuilder.css` and the corpus renders' computed styles (provenance comment on every rule group in `src/buildhub-preview/stylesheet.ts`); the Bootstrap 5 grid subset is MIT. Fonts are SIL OFL 1.1 from Google Fonts. Nothing in this folder is copied from iMIS's stylesheets. The icon sprites and logo under `shell-assets/` are iMIS artwork, copied byte for byte with their provenance (see "Renderer 1.4.0").
